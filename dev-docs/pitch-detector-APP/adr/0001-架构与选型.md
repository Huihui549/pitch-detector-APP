## 0001 Qt 6.8.3（LTS）作为目标框架版本

- **日期**：2026-09-28
- **状态**：已接受（待用户最终确认授权方式）
- **背景**：在线安装器可选 6.12.0-rc / 6.11.2 / 6.11.1 / 6.10.3 / 6.9.3 / 6.8.3 / 6.7.3 / 6.5.3，需定一个长期可用的版本。
- **选项**：
  - A `6.8.3`（LTS）
  - B `6.11.2`（最新标准版）
  - C `6.12.0-rc`（预发布）
  - D `6.5.3` / `6.7.3` / `6.9.3`（已 EOL）
- **决定**：选 A **6.8.3**。
- **理由**：
  1. 6.8 是候选列表中**唯一仍在支持期内**的 LTS 线，商业支持至 **2029-10-08**（[endoflife.date/qt](https://endoflife.date/qt)）
  2. 6.11 的开源支持已于 **2026-09-22 结束**；6.9 / 6.7 / 6.5 两条支持线均已终止
  3. 6.12 的计划正式发布日为 **2026-09-30**（[Qt Wiki 发布计划](https://wiki.qt.io/Qt_6.12_Release)），此刻只有 RC，不用于生产
  4. 第三方库、教程、Stack Overflow 覆盖最好，跨平台（Windows / Android / 嵌入式）经验最成熟
- **代价与遗留**：
  - 开源用户的 LTS 与标准版同待遇：6.8 的免费补丁停在 2025-04，**6.8.4 及以后仅商业授权可得**（Qt 公司 2020 年起政策）
  - 若后续需要更新特性（如 Qt 6.11 的新音频 API），升级路径需重新验证算法链路
  - 6.10 是否为 LTS 在公开资料中存在冲突（表格未标 LTS），若用户确认其为 LTS，需重开本决策
- **来源功能**：pitch-detector

## 0002 QML 纯界面 + C++ 算法与流程，四层单向依赖

- **日期**：2026-09-28
- **状态**：已接受（用户明确要求）
- **背景**：上游网页版把算法与界面混在单文件里，曾出现同一算法三份副本、结论分叉（pitfalls #22）。重写为 Qt 应用时若不正视分层，会重蹈覆辙。
- **选项**：
  - A QML 承载全部逻辑（JS 内联算法）
  - B C++ 与 QML 混写界面，算法散落
  - C **QML 纯界面 + C++ 分层**（core / audio / io / app），依赖单向
- **决定**：选 C。
- **理由**：
  1. 算法为纯逻辑，放 `src/core/` 可**脱离 UI 单测**，直接对 88 键素材回归
  2. 采集层（`src/audio/`）抽象为接口，嵌入式设备只需新增实现，不动上层
  3. QML 只做展示与交互，界面改动不触发算法回归
- **代价与遗留**：
  - 多一层 C++ 类型注册与属性/信号样板，首版开发量增加
  - 调试实时数据要跨 QML/C++ 边界，需在调试界面暴露足够内部量（对应上游 `detectWithCurve` 的做法）
- **来源功能**：pitch-detector

## 0003 以 JS 引擎为唯一真值，做跨语言一致性验证

- **日期**：2026-09-28
- **状态**：已接受
- **背景**：上游 `pitch-engine.js` 的 84/88 命中率是实测结论，其参数（阈值 0.3、窗长阶梯、浅谷阈值 0.15…）都是从失败方案里筛出来的，凭理解重写极易丢细节。
- **选项**：
  - A 按文档重写 C++，靠人工核对参数
  - B C++ 重写 + **逐帧对拍**上游 JS 引擎（同输入同输出）
- **决定**：选 B。
- **理由**：
  1. 上游引擎可被 Node 直接调用（`tools/wav-read.mjs` + `verify-engine.mjs` 已具备读取与判定能力），对照端零成本
  2. 逐帧对拍能量化"重写是否引入了偏差"，把"看起来一样"变成"数字一样"
  3. 对拍脚本可长期作为回归项（上游任何参数改动都能立刻发现）
- **代价与遗留**：
  - 需要一次性工具：Node 侧导出逐帧 CSV 的桥接脚本
  - 允许的差异必须写清（浮点末位、JSON 序列化精度），否则会出现"永远对不齐"的假失败
- **来源功能**：pitch-detector

## 0004 实时链路不复用文件分析的级联窗长

- **日期**：2026-09-28
- **状态**：已接受（2026-09-28 用户拍板：先沿用固定窗，实测后再调）
- **背景**：上游文件分析用 `[1024…16384]` 级联窗覆盖全 88 键；实时链路用固定窗 4096（82–1050 Hz），因为级联代价高。Qt 侧窗口可用更长，但延迟会同步增长。
- **选项**：
  - A 实时也走级联窗长（覆盖全键盘，延迟最大 16384 样点 ≈ 371 ms @44.1 kHz，明显超标）
  - B 实时沿用固定窗（上游结论），音域受限
  - C 实时用"限定两档窗长"（如 2048 / 4096），在延迟与音域间折中
- **决定**：**暂定 B**，待采集链路实测后按数据裁定（延迟、低音识别率两项）。
  - 2026-09-28 用户确认采用本项；**切换条件前置声明**：实测端到端延迟 > 200 ms，或吉他六弦（E2=82.41 Hz）识别率低于 80%，则改评选项 C（2048+4096 两档），并同步更新 `spec.md` 的音域与延迟指标。
- **理由**：上游 ADR-0001 已记录"实时代价"是音域收口的直接原因；在无实测延迟数据前不做激进改动。
- **代价与遗留**：实时链路音域低于文件分析，界面必须显式标注当前模式的音域，避免用户误判。
- **来源功能**：pitch-detector

## 0005 音频采集抽象为 IAudioSource，预留嵌入式实现

- **日期**：2026-09-28
- **状态**：已接受
- **背景**：目标含"后续嵌入式设备运行"，嵌入式通常不走 Qt Multimedia，而是 ALSA / 厂商 SDK。
- **选项**：
  - A 直接调用 Qt Multimedia，嵌入式时再重构
  - B 定义 `IAudioSource` 接口 + `QtAudioSource`（桌面/手机）+ 嵌入式实现预留
- **决定**：选 B。接口最小化为五项：开启（含格式请求）/ 停止 / 查询实际格式 / 样点回调 / 错误信号。
  - **首版落地的实现有两个**：`QtAudioSource`（桌面 + Android）与 **`FileAudioSource`（把 WAV 按实时速度喂入）**——后者不是产品功能，而是把"实时链路"变成可自动回归的测试手段（上游该链路从未被验证过）。
  - `EmbeddedAudioSource` **只保留接口位置，不写空实现**（R8：现在没人用 → 不写）。
- **理由**：把"平台差异"封在唯一一层，上层（core/app）完全不感知采集来源；符合低耦合要求且成本可控。
- **代价与遗留**：接口若设计过宽会变成 YAGNI（R8）；**嵌入式实现真正落地前不新增接口方法**。
- **来源功能**：pitch-detector

## 0006 首版手机优先、单页 + 底部导航、调试页隐藏

- **日期**：2026-09-28
- **状态**：已接受（用户拍板）
- **背景**：需定首版的平台次序、界面骨架与调试能力是否随发布暴露。
- **选项**：
  - 平台：桌面优先 / **手机优先** / 双端同时
  - 界面：三标签页（沿用上游）/ 侧边导航 + 页面栈 / **单页 + 底部导航栏**
  - 调试页：进首版作为正式页 / **进首版但隐藏入口** / 后置不做
- **决定**：
  1. **手机（Android ARM64-v8a）优先**；桌面版同代码库一并构建，承担开发期快速验证
  2. **单页 + 底部导航栏**：实时 / 文件 / 音域 / 更多（四入口）
  3. **调试页进首版，作为隐藏入口**（连续点击标题区 N 次进入，N=7，不做菜单项）
- **理由**：
  1. 手机是上游的真实使用场景（练琴/练唱时手持），优先可让真机验证尽早开始；桌面版作为开发效率工具不额外花成本
  2. 底部导航是移动端最省心智的骨架，单手可达；桌面端同一 QML 结构加宽即可用
  3. 调试页（τ 谷值曲线、RMS、实际采集格式）是排查"为什么测不准"的唯一工具（上游 `debug.md` 整套流程依赖它），必须进首版；但普通用户不需要，隐藏入口兼顾两者
- **代价与遗留**：
  - 手机优先意味着 **Android 工具链（SDK/NDK/JDK/Gradle）必须先装**，环境成本前置
  - 隐藏入口需在 `AGENTS.md` 与验收项中写清进入方式，否则后续自己也会找不到
  - 桌面端在移动骨架下的宽屏布局需额外适配（第二优先，首版可只保证可用）
- **来源功能**：pitch-detector

## 0008 C++ 标准采用 C++20（而非 C++17）

- **日期**：2026-09-28
- **状态**：已接受
- **背景**：架构草案写的是 C++17（以"Qt 6.8 基线"为由）。首次编译时，算法层用了 `std::span`（C++20）——
  编译器直接报错（`'std::span' is only available from C++20 onwards`）。必须在"升标准"与"改类型"之间选一个。
- **选项**：
  - A 保持 C++17，把 `std::span` 换成 `const float* + std::size_t` 的自造视图
  - B 升到 C++20，保留 `std::span`
  - C 保持 C++17，继续用 `std::vector<const float>` 拷贝传递
- **决定**：选 **B（C++20）**。
- **理由**：
  1. `std::span` 正是"任意长度样点视图"这一接口最贴切的类型；选项 A 是自造轮子且**丢掉边界信息**（指针+长度靠调用方自觉，正是本项目要防的那类隐患）
  2. 选项 C 会在热路径上引入逐帧拷贝（R8：热路径禁大块拷贝）
  3. **Qt 6.8.3 官方要求 C++17 或更高**，故 C++20 与 Qt 不冲突；工具链侧实测 GCC 16.2.0 与 MSVC 2022 均支持
- **代价与遗留**：
  - 提升了编译器最低版本要求（嵌入式交叉工具链若过旧需评估；本项目的嵌入式部分尚未落地，届时再验）
  - `AGENTS.md` 与 `design/architecture.md` 中的 C++17 表述必须同步（R1 第七节级联扫描）
- **来源功能**：pitch-detector

## 0009 实时链路改用两级窗长（4096 + 16384），取代上游的固定 4096

- **日期**：2026-09-28
- **状态**：已接受（部分取代 ADR-0004 的窗长策略）
- **背景**：ADR-0004 决定首版沿用上游"实时固定窗 4096"。实现实时控制器时暴露一个硬冲突：
  4096 样点窗只能可靠覆盖约 82–1050 Hz，而**首版就要能测钢琴与吉他**——
  吉他六弦 E2=82.41 Hz 勉强可用，钢琴 A0=27.5 Hz（周期 1604 样点）在 4096 窗里装不下足够周期，
  必然判不出。用户的目标形态（手机 APP 测钢琴/吉他）与"固定 4096"直接矛盾。
- **选项**：
  - A 保持固定 4096，实时链路音域受限（82–1050 Hz），低音不可测
  - B 实时也走完整级联（1024→16384）：低延迟档失效，最长窗需要攒够 16384 样点
  - C **两级窗长**：先 4096（低延迟，中高音即刻可用），无效再试 16384（低音）
- **决定**：选 **C**。
- **理由**：
  1. 4096 窗在中高音上本来就够用且延迟最低，不必为低音牺牲它
  2. 低音只在 4096 判不出时才多花一次 16384 窗的计算，代价可控
  3. 与算法内部"τ 区间按音域收口"的既有逻辑一致，**不改变任何判据**（只是换窗长）
- **代价与遗留**：
  - 启动后约 0.65 s 内（攒够 16384 样点之前）低音不可测——界面不提示，属可接受
  - 触发 16384 档时单帧计算量显著上升（差分函数代价按窗长平方增长）：低频段需实测 CPU 占用
  - 必须实测端到端延迟并记录（spec D3）；若超过 200 ms，按 ADR-0004 的切换条件重新裁定
- **来源功能**：pitch-detector

## 0011 `readWavMono` 的路径参数统一为 UTF-8（取代"宽/窄双入口"）

- **日期**：2026-09-30
- **状态**：已接受
- **背景**：坑 A29 的处置是给 `readWavMono` 加一个 Windows 专用的宽字符重载 `readWavMonoW(std::wstring)`，Qt 侧用 `QString::toStdWString()` 调它。该方案在 Windows 上正确，却把"平台知识"推给了每个调用点：声明与实现都在 `#if defined(_WIN32)` 内，而调用点按无条件调用写，于是 Windows 编得过、Android 三处全部编不过（坑 A38）；且 `wchar_t` 在 Android 是 UTF-32，宽字符入口本身没有跨平台语义。
- **选项**：
  - A 每个调用点各自 `#if defined(_WIN32)` 分支（宽字符 / UTF-8 窄字符）
  - B **统一入口**：`readWavMono(const std::string&)` 的路径约定为 UTF-8，Windows 分支内部转 UTF-16 后走既有 `CreateFileW` 代码，非 Windows 直接用窄字符 `ifstream`
  - C 保持双入口，只在 Android 上砍掉受影响的功能
- **决定**：选 **B**。
- **理由**：
  1. 同一逻辑出现在 3 个调用点，按 R8 应提取为单一实现；调用点不再需要平台知识，A38 那类"漏加守卫"不可能再发生
  2. Android/Linux 的文件名本就是 UTF-8 字节，选 UTF-8 是**顺平台**；Windows 侧仍是原来的 `CreateFileW` 实现，中文路径能力（A29）不变——已用中文路径素材实测回归
  3. 现有 ASCII 调用方（`tools/cross-check`、`tests/core-tests`）无需改动：ASCII 是合法 UTF-8
- **代价与遗留**：
  - Windows 分支多一次 UTF-8→UTF-16 转换（每次打开文件一次，非热路径）
  - `readWavMonoW` 保留，但**只供 Windows 专有工具**（`tools/piano-batch` 从宽字符命令行取路径）；Qt 侧一律走 UTF-8 入口
  - 误用 `QString::toStdString()`（本地代码页）会在中文路径上失败——已写进 `wav-reader.h` 的接口注释
- **来源功能**：pitch-detector

## 0012 界面风格定稿：D（仪表深色高对比）+ E（Carbon 规则）

- **日期**：2026-09-30
- **状态**：已接受（用户 2026-09-30 选定；界面实现随本 ADR 落地）
- **背景**：首版界面只有"能用"的默认配色（`theme.h` 里 10 个色值 + 4 个字号，无风格定义），用户要求**先定风格再继续改界面**，并明确"后续开发全部统一风格"。候选 7 个方向（链接均实测可达）。
- **选项**：
  - A Material 3（Qt 自带 Material 风格）・B iOS / Apple HIG ・C Fluent 2 / Qt Universal
  - **D 仪表/DAW 深色高对比** ・ **E IBM Carbon（数据密集场景）** ・F Glassmorphism ・G Neumorphism
- **决定**：选 **D + E**——D 定视觉基调，E 提供色板/栅格/字号的**规则**。
- **理由**：
  1. 使用场景是"练琴/练唱时瞄一眼"：**弱光可读、一眼看清读数**比"通用 App 观感"重要
  2. 主信息只有"音名 + 音分 + 曲线"，仪表风格天然贴合；E 的 8px 栅格与克制灰阶能防住"自由发挥导致的不统一"
  3. 实现成本最低、低端机友好：不引入模糊/大阴影（F/G 在千元机上掉帧，且会降低读数对比度）
  4. 与既有骨架不冲突（ADR-0006 单页+底部导航、ADR-0010 手机比例 400×860），只换配色与排版令牌
- **代价与遗留**：
  - 深色主调在强光户外可读性一般（练琴以室内为主，接受）
  - 单一强调色的约束意味着：**后续新增状态色必须先在 `theme.h` 定名并写明语义**
  - 引入第三方图标资源（Lucide，ISC）→ 需持续维护 `resources/ATTRIBUTION.md`
  - 风格一致性由 `tools/check-theme.ps1` 机械把关（已做负向验证，坑 A13）
- **来源功能**：pitch-detector

## 0013 增加浅色主题，主题可在「更多 → 外观」切换并持久化

- **日期**：2026-09-30
- **状态**：已接受（用户要求："增加一个白色的浅色主题色"）
- **背景**：ADR-0012 定稿的是**深色**（D 风格）。用户在手机上看到实际效果后要求补一套**白色浅色**主题，并能在界面里切换。
- **选项**：
  - A 只加深色（不切）—— 与用户要求不符
  - B **两套配色 + 界面切换**：同一套令牌名，`mode = dark | light`
  - C 跟随系统深浅色（Android 12+ 有系统主题，但桌面端与旧机型行为不一致，且用户要的是手动切换）
- **决定**：选 **B**。默认 `dark`，切换入口在「更多 → 外观」（深色/浅色两个按钮 + `moon`/`sun` 图标），选择写入 `QSettings`（`ui/themeMode`）并**重启保持**。
- **理由**：
  1. **令牌名不变、只换取值** —— 所有 QML 一行都不用改就能跟随切换，这正是 ADR-0012 把颜色收进令牌的收益
  2. 场景互补：深色适合弱光/舞台，浅色适合强光/白天；不给用户选择只能二选一硬编码
  3. 代价可控：只是 `theme.h` 里每个颜色多一个三元表达式 + 一个 `modeChanged` 信号
- **代价与遗留**：
  - **颜色属性必须从 `CONSTANT` 改为带 `NOTIFY modeChanged`**：`CONSTANT` 的属性即使值变了也不会让 QML 绑定重算 → 界面不重绘（这是本轮最容易踩的一点）
  - 浅色态的 `accent` 必须比深色态**更深**（`#0f8b7c` vs `#2ed3b7`），否则白底上对比度不足；状态色同理（`ok`/`warn`/`danger` 各有一套）
  - 未做"跟随系统"（选项 C）：以后要做的话，`mode` 增加一个 `system` 取值即可，令牌层不用动
  - `--theme <dark|light>` 命令行开关只改内存、**不落盘**，供截图/排查使用（避免自动化脚本改掉用户偏好）
- **来源功能**：pitch-detector

## 0014 页面三段结构：标题区 / **可滚动**内容区 / 底部导航

- **日期**：2026-09-30
- **状态**：已接受（用户要求："每个页面应该都是分为三部分……内容区应该可以上下滑动"）
- **背景**：ADR-0006 定的"单页 + 底部导航"只规定了骨架，没规定内容区**装不下时怎么办**。实际结果是各页把卡片塞进 `ColumnLayout`，超出的部分被裁掉且**无法滑动**（手机上很明显：主屏 6 张卡、文件页摘要+曲线+表格）。
- **选项**：
  - A 各页自己写 `Flickable` + 滚动条
  - B **统一滚动容器组件** `components/PageScroller.qml`，页面只管往里放卡片
  - C 压缩内容使其必然放得下（放弃信息量）
- **决定**：选 **B**。
- **理由**：
  1. 三段结构固定后，"哪块滚动、哪块不动"不再每次讨论：**标题区与底部导航固定，只有内容区滚**
  2. 滚动细节（细滚动条样式、停止回弹、装得下时自动隐藏、宽度避让滚动条）收在一处 → 不会各页漂移（与 ADR-0012 的"令牌收口"同一思路）
- **代价与遗留**：
  - **滚动容器里 `Layout.fillHeight` 失去意义**（高度由内容决定）：各页原先靠它撑满的部分改为固定高度（主屏曲线 220、文件页曲线 170、调试页 τ 曲线 190）
  - 文件页的逐帧表格是**嵌套滚动**（表格在卡片内自己滚）：手机上是可接受惯例，但不要再往上加嵌套层
  - 装得下时不显示滚动条（`ScrollBar.AlwaysOff`），避免"没得滚还画一条"
- **来源功能**：pitch-detector

## 0015 存储访问：以系统选择器为准，不追求"看到所有文件"

- **日期**：2026-09-30
- **状态**：**已接受**（实测否决 C 档；`MANAGE_EXTERNAL_STORAGE` 已按用户决定从清单删除，只保留诊断能力）
- **背景**：用户实测"用本程序的『选择文件』看内部存储的 `Android` 目录，只有 media 与 obj 两个文件夹，而手机自带文件管理器里有很多"。同时用户从 QQ 传到手机的测试音频（`tone (49) - A4.wav` 等）恰好落在 `/sdcard/Android/data/com.tencent.mobileqq/Tencent/QQfile_recv/`——**整机仅有的 2 个 `.wav` 都在这个目录里**，即"选不到文件"的真实成因。
- **选项**：
  - A 保持**系统选择器**（Qt 6.8 的 Android 平台插件内含 `QAndroidPlatformFileDialogHelper`，走 SAF；系统对 `OPEN_DOCUMENT` 的解析结果是 `com.android.documentsui/.picker.PickActivity`），零改动
  - B 应用内自建文件浏览器 + 运行期申请 `READ_EXTERNAL_STORAGE`(≤API 32) / `READ_MEDIA_AUDIO`(API 33+)
  - C 在 B 之上再加 `MANAGE_EXTERNAL_STORAGE`（"所有文件访问权限"），目标就是 `Android/data`、`Android/obb`
- **决定**：**保留 A**；C 经同机 A/B 实测**被否决**——它换不到那两个目录。
- **实测证据**（HUAWEI ADY-AL10 / Android 12 / API 31；同机同代码，只切换 appops）：
  | 探测项 | 未授权 | 已授权（`Environment.isExternalStorageManager()` 实测为 true） |
  |---|---|---|
  | `/sdcard/Android/data` | 可读=否，0 项 | 可读=否，**0 项** |
  | `/sdcard/Android/obb` | 可读=否，0 项 | 可读=否，**0 项** |
  | `/sdcard/Android/media` | 可读=是，3 项 | 可读=是，3 项 |
  | `/sdcard/Android` | 4 项（data / media / obb / obj） | 4 项 |
  | `/sdcard` | 15 项 | 18 项 |
  | `/sdcard/Download` | 3 项（只列出目录） | 5 项（多出 `.zip`、`.dat` 等**非媒体**文件） |
- **理由**：
  1. Android 11（API 30）起 `Android/data` 与 `Android/obb` 对**所有第三方应用**封锁（系统选择器里根本看不到，SAF 也不允许授权该文件夹）；本次实测进一步确认 `MANAGE_EXTERNAL_STORAGE` **同样打不开**，它只放宽了公共目录里非媒体文件的可见性。
  2. 手机自带文件管理器能进那两个目录，是因为它是**系统特权应用**——第三方应用无 root 无法复制这条能力（需 root/Xposed 模块才能解除该限制）。
  3. 因此"应用内自建浏览器"（B）**不增加任何可见范围**，只改变界面形态；对"选一段 wav"这个真实需求没有收益。
  4. 本程序只读非压缩 PCM WAV（属媒体文件），公共目录里的音频用系统选择器已经能选中。
- **代价与遗留**：
  - 音频必须放在**公共目录**（`Download` / `Music` / `Documents`）才能被选到；QQ/微信接收的文件默认落在 `Android/data`，需要用户手动"另存为/移动"到公共目录
  - `android/AndroidManifest.xml` 里的 `MANAGE_EXTERNAL_STORAGE` 已验证完毕并**删除**（实测它换不到那两个目录，且属 Google Play 高风险权限）；清单里留了一段注释记录"为什么故意不申请"，避免以后有人又加回来
  - `StorageAccess`（`src/app/storage-access.{h,cpp}`）保留为**诊断**：Debug 页「存储访问」卡片显示探测报告；手机端亦可用 `adb shell run-as org.pitchdetector.app cat files/storageprobe.txt` 读取
  - 若将来做 B 档（应用内自建浏览器，目前未做），权限应选**最小必要**的 `READ_MEDIA_AUDIO`，不要用 `MANAGE_EXTERNAL_STORAGE`
- **来源功能**：pitch-detector
